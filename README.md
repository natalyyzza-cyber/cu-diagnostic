# Диагностика городского проекта

Лид-магнит курса [«Школа городских продюсеров»](https://cityuniversity.ru/school-urban-producers) (Городской университет 2.0).
Человек за 7–10 минут проходит опрос из 15 вопросов и сразу получает оценку проекта по методике С. Мурунова, сильные стороны, зоны роста, потенциал, ближайший шаг, роадмап на год и две CTA-кнопки.

## Запуск

```bash
npm install
cp .env.example .env   # заполнить OPENAI_API_KEY и ADMIN_PASSWORD
npm start              # http://localhost:3000
npm test
```

Нужен Node.js 22.9+.

## Как это устроено

| Путь | Что там |
|---|---|
| `public/js/questions.js` | Вопросы, варианты ответов и баллы. Общий файл для браузера и сервера |
| `src/scoring.js` | Подсчёт баллов Q5–Q14 (максимум 17), интерпретация, выбор сильных сторон и зон роста, шаблонные тексты и роадмап |
| `src/ai.js` | Персонализация текстов через Responses API / совместимого провайдера: правила методики собраны в системном промпте |
| `src/store.js` | Хранение заявок: на Netlify — Netlify Blobs, локально — `data/submissions.json` |
| `src/app.js` | API, страница `/admin` и выгрузка CSV (Hono, стандартные Request/Response) |
| `src/personalize-job.js` | Фоновая персонализация результата |
| `server.js` | Локальный сервер |
| `netlify/functions/` | Функции Netlify: `api.mjs` (API и админка), `personalize-background.mjs` (персонализация, до 15 минут) |
| `public/` | Интерфейс: стартовый экран, опрос, результат |

### Сценарий

1. **Старт.** Пользователь вводит ФИ, email и профиль (B2C/B2B, для информации) и даёт согласие на обработку ПД. Контакт сохраняется сразу, ещё до ответов.
2. **Опрос.** Один вопрос на экран, прогресс-бар, кнопка «Назад». Ответы хранятся в `localStorage`, поэтому после перезагрузки можно продолжить. Сервер запоминает номер вопроса, на котором человек остановился.
3. **Результат** показывается мгновенно: баллы и шаблонные тексты считает код по методике. Затем запускается фоновая персонализация через Responses API / совместимого провайдера; страница опрашивает статус, и тексты сильных сторон, зон роста, потенциала, ближайшего шага и роадмапа заменяются персонализированными. ФИО и email в запрос к модели не передаются; свободный текст Q4 всё же должен содержать только сведения, необходимые для диагностики. ИИ не меняет баллы и выбор показателей. Если ключа нет или запрос не удался, остаётся шаблонная версия.
4. **CTA:** консультация и запись в ШГП. Клики учитываются в админке. Результат открывается по постоянной ссылке `/r/<id>` и сохраняется в PDF через печать.

### Правила методики, принятые в коде

- **Итоговый балл.** Сумма Q5–Q14 (максимум 17) сохраняется как внутренний ориентир. Пользователь не должен воспринимать его как оценку качества проекта. Главный вывод строится не из суммы, а из ограничения следующего шага.
- **Стадия Q1.** Влияет на приоритеты диагностики. Для ранних стадий отсутствие регулярной работы, автономной команды и устойчивой модели не считается самостоятельной проблемой.
- **Четыре слоя диагностики.** Результат собирает картину через ценность проекта (Q5, Q8), практику и обучение (Q9, Q10), востребованность (Q12), ресурсную модель (Q11, Q13) и способность проекта продолжаться без постоянного участия автора (Q6, Q14). Q7 показывает широту управленческих ролей автора, а не заменяет оценку команды.
- **Q8.** Внутри матрицы отдельно учитываются три блока: ценность, реализация и устойчивость. Одинаковое число «Да» в разных блоках не считается одинаково полезным.
- **Q12 — ключевой валидатор.** Самооценка понимания проекта не считается достаточным доказательством востребованности. Чем ближе ответ к наблюдаемому поведению людей, тем надёжнее вывод.
- **Q11.** Ресурсная модель включает деньги, время, людей, площадки, партнёрскую и городскую поддержку и другие необходимые ресурсы. Не предполагается наличие плательщика.
- **Q13.** Количество ресурсов остаётся вспомогательным ориентиром. В результате дополнительно определяется предполагаемый критический ресурс ближайшего шага с учётом формата и стадии.
- **Главное ограничение.** Из релевантных для стадии показателей выбирается один bottleneck: он учитывает разрыв до максимума, значимость для текущей стадии и наличие/отсутствие практических подтверждений. Q15 не может механически переопределить этот вывод.
- **Сильные стороны.** Это не просто «самые высокие баллы»: они показывают уже собранные элементы, которые можно использовать как опору следующего шага. Они выбираются только среди максимальных показателей.
- **Зоны роста.** До трёх зон — это поддерживающие ограничения вокруг главного фокуса. Они не выбираются только по минимальному абсолютному баллу.
- **Надёжность.** Высокая надёжность требует нескольких независимых признаков практического опыта: действие, анализ опыта, проверка востребованности и понимание модели. Противоречия и преобладание самооценки снижают уровень до «предварительной».
- **Противоречия.** Проверяются несогласованные ответы: стадия и действия, команда и автономность, заявленный спрос и отсутствие реализации/анализа, неопределённая аудитория и одновременно полностью собранная модель. Они не считаются ошибкой участника, но ограничивают уверенность вывода.
- **Q4.** Свободное описание проблемы не превращается в балл, но используется ИИ для проверки связности проблемы, аудитории, формата и результата. ИИ не имеет права придумывать факты.
- **Q15.** Это субъективный запрос участника. Система сравнивает его с главным ограничением и объясняет расхождение, если сначала нужно решить более базовую задачу.
- **Ближайший шаг.** Это одно проверяемое действие, которое должно либо закрыть главное ограничение, либо дать новый факт для следующего решения.
- **Роадмап.** Это последовательность действий, а не список пожеланий: первые шаги дают доказательства и закрывают ограничения, следующие зависят от полученных результатов.
- **ИИ.** ИИ не меняет баллы, главное ограничение, выбранные сильные стороны и зоны роста. Он персонализирует объяснение, связывает выводы с фактическими ответами и строит последовательный роадмап. Для официального OpenAI используется Responses API со `store: false`; при `OPENAI_BASE_URL` обработка происходит у указанного провайдера, поэтому его условия хранения и обработки данных нужно проверить отдельно.

## Администрирование

`/admin` защищена HTTP Basic: логин любой, пароль из `ADMIN_PASSWORD`. На странице таблица заявок (ФИ, email, профиль, статус, стадия, формат, баллы, запрос, клики по CTA, ссылка на результат) и кнопка «Скачать CSV» со всеми ответами и UTM-метками.

## Деплой на Netlify

Проект готов к Netlify: `netlify.toml` в корне, статика из `public/`, API в функциях, заявки в Netlify Blobs (хранилище сайта, не пропадает между деплоями).

1. Netlify → **Add new project → Import an existing project → GitHub**, выбрать репозиторий `cu-diagnostic` и ветку. Настройки сборки подтянутся из `netlify.toml`.
2. **Project configuration → Environment variables**: `OPENAI_API_KEY`, `ADMIN_PASSWORD`, `PRIVACY_POLICY_URL` (при необходимости `OPENAI_BASE_URL`, `OPENAI_MODEL`, `CONSULTATION_URL`, `SCHOOL_URL`). Переменные должны быть доступны в scope **Functions**. Если используется `OPENAI_BASE_URL`, отдельно проверьте договор и правила обработки данных выбранного провайдера.
3. **Deploy**. Каждый следующий пуш в выбранную ветку деплоится автоматически.

Персонализация на Netlify идёт в фоновой функции (Background Functions, до 15 минут), поэтому не упирается в лимит 60 секунд обычной функции.

Локально без Netlify заявки пишутся в `data/submissions.json`.


## Проверка реального AI-провайдера

Обычный `npm test` не тратит API-кредиты: интеграционный прогон LLM запускается только при `DIAGNOSIS_LLM=1`.

Для ручной проверки полного пути на 8 синтетических сценариях:

```bash
DIAGNOSIS_LLM=1 npm test -- test/diagnosis-formats.test.js
```

Тест проверяет, что реальный провайдер возвращает персонализированный результат и не меняет общий балл и выбранные зоны роста. В GitHub Actions добавлен ручной smoke-test; он запускается только если в Secrets задан `OPENAI_API_KEY`.
